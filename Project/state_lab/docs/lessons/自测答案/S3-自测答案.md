# S3 自测答案（对照版）

> 2026-07-16 归档。本课起改为一次性完成模式（学员自行阅读学习），答案与课后练习均为讲师直接给出的对照版。

## 自测清单答案

### 1. Cubit 和 Bloc 怎么选？MiniShop 三个状态件各选了哪个、为什么？

看**有没有事件流转换需求**。Cubit 无 event 层、方法直接 emit，轻量；Bloc 的事件流可挂 EventTransformer（防抖/丢弃/排队/掐旧）。购物车增删是简单"方法→新状态"→ `CartCubit`；列表 LoadMore 要 `droppable` 防重入 → `ProductListBloc`；搜索要 `debounce+restartable` → `SearchBloc`。

### 2. emit 一个和当前值相等的 state 会怎样？和 Equatable 什么关系？

`emit` 内部 `if (newState == state) return;`——短路，不发流、不重建。这里的 `==` 就是 Equatable 提供的值语义（props 逐项比较）。没有值语义 `==`（默认引用相等），两个内容相同的新旧对象恒不等，该省的重建一次也省不下。

### 3. buildWhen 返回 false 时发生什么？和 BlocSelector 什么关系？

state 流照样推来新状态（listener 照样收到），只是 `BlocBuilder` 跳过这次 build——**通知已到达，重建被拦下**。BlocSelector 是它的字段版语法糖：先 `selector` 选出 R 再比 `==`，等价于 `buildWhen: (p, c) => selector(p) != selector(c)` + builder 只拿 R。

### 4. 为什么防抖放 EventTransformer 而不在 TextField 里 setState 计时？

事件流是 Bloc 的一等公民，去抖是**对流的变换**，属于状态层：可单测（blocTest 直接断言只发最后一枪）、可复用、页面零逻辑。放 UI 层 = 流逻辑漏进视图，测试只能 pumpWidget 真等 400ms。

### 5. droppable 和 restartable 分别替掉了 v1 的哪行手写？

`droppable()` ← `if (_loadingMore) return;`（忙时丢弃新事件 = 布尔防重入的声明式替身）；`restartable()` ← 请求序号 `seq != _requestSeq` 丢过期（新事件 switchMap 掐掉旧处理器，旧响应回来时 emit 已 no-op）；配上 `debounce` 再替掉 `Timer` 防抖。

### 6. 不可变 CartLine 相比可变 CartItem 多写了什么、换回了什么？state 塞可变字段会出什么 bug？

多写：字段全 final、`copyWith`、`Equatable props`（copyWith 税）。换回：值语义 `==` → emit 短路省重建、buildWhen 可声明式判断"变了什么"、状态序列可断言可回放、类型级杜绝"绕过通知偷偷改"。塞可变字段的两个方向 bug：就地改字段后 emit 同一引用 → `==` 恒真被短路，**界面不更新**；或 props 含每次新建的可变集合 → 恒不等，该省的重建全没省。

### 7. RepositoryProvider 和 BlocProvider 区别？

RepositoryProvider 放**不通知的服务/仓库**（纯 DI，UI 不随它变），= Provider 世界的 `Provider<T>`；BlocProvider 放 Bloc/Cubit（托管 close、UI 订阅 state 流）。

### 8. BlocListener 相比 BlocBuilder 什么时候用？副作用写进 builder 会怎样？

一次性副作用（SnackBar/导航/弹窗）用 Listener——每次状态变化**恰好执行一次**、不参与重建；builder 是"状态→UI"的纯投影，随时可能被框架多跑（父重建、热重载），写副作用会重复触发。`listenWhen` 可限定只在特定转移时触发（v2 搜索页：仅"刚转入 failure"弹一次）。

### 9. v1 的 _disposed 守卫在 v2 去哪了？为什么可以不写？

框架接管了。bloc `close` 后 `Emitter` 进入 isDone，`emit` 变 no-op；`restartable/droppable` 还会主动取消旧处理器订阅。v1 的病根"页面 pop 后在途请求回来撞 used-after-disposed"在 Bloc 侧不存在。极端场景手动判用 `if (isClosed) return;`。

### 10. 不可变状态的三样红利、三样代价？（S2 练习 2 正式答案）

红利：①可 diff/判等（emit 短路 + 声明式 buildWhen）；②可回放（状态序列 = 完整录像，blocTest `expect: [A,B,C]`）；③类型级根治"绕过通知偷偷改"。代价：①每个 state 要 copyWith + `==`/hashCode 样板（Equatable/freezed 减负）；②改一个字段要整体复制替换；③心智从"调方法"换成"事件进、状态出"。

## 课后练习对照（理论推演版）

**练习 1（droppable → concurrent）**：快速触底两次会起两个并发处理器，各自 `fetchProducts(skip: state.skip)` 读到**同一个 skip**——两次请求拉同一页，`items` 追加两遍（列表出现重复商品），`fetchCalls` 翻倍。droppable 语义下第二次触底事件直接被丢，一次请求、一次追加。

**练习 2（restartable → sequential）**：sequential 排队执行——旧词的慢请求做完才轮到新词。若旧请求响应慢于新请求（服务端波动），排队保证了顺序所以不会"旧盖新"；但真正的问题是**旧词的结果会先展示一遍**（用户已经改词了还闪一下旧结果），且每一枪都必须等完，浪费且滞后。restartable 直接掐掉旧处理器，永远只有最新那枪活着。

**练习 3（带去 S4 的思考）**：GetX 的答案是"都给你"：`.obs` 一把梭接近 setState 的随手改，`GetxController`+workers 可按需上结构，还附赠路由/DI/工具全家桶。权衡点在于：便利来自**全局注册表 + 不依赖 context**，代价是依赖关系离开了 Widget 树（编译器和树都帮不了你），纪律全靠团队自觉——S4 的专节就讲这个边界。
