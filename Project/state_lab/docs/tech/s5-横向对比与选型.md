# s5 · 横向对比与选型：同一个 MiniShop 的五种答案

> StateLab 技术文档第五篇（S5 课配套），全系列的收官对比。前置：[s1-地基](s1-状态管理的地基.md) · [s2-provider](s2-provider.md) · [s3-bloc](s3-bloc.md) · [s4-getx](s4-getx.md)。
> 对比素材全部来自 `lib/versions/` 下五份**规格逐像素一致**的 MiniShop 实现——任何两版的 diff 就是纯粹的状态管理差异。Riverpod 版（v4）为 S6 结课作业，本文的 Riverpod 代码即其参考写法。

## 0. 一张总表

| | v0 setState | v1 Provider | v2 Bloc | v3 GetX | v4 Riverpod |
|---|---|---|---|---|---|
| 心智模型 | "改完自己刷" | 树上共享对象 + 通知 | 事件进、状态出 | 全局表 + 双轨通知 | 树外声明式 provider 图 |
| 依赖宿主 | 构造函数层层传 | Widget 树（InheritedWidget） | Widget 树（同左） | **树外全局可变 Map** | **树外不可变 provider 图**（Scope 定容器） |
| 状态可变性 | 可变 | 可变 + notify | **不可变 + emit** | 可变 + Rx/update | 不可变整体替换为主 |
| 跨路由 | 传参 | `.value` re-provide | `BlocProvider.value` | 不存在此问题 | 不存在此问题（container 跨路由，见 v4 注） |
| 重建收窄 | 无（整页） | Selector / select | buildWhen / BlocSelector | Obx 天然小粒度（无字段判等） | `select` / 细拆 provider |
| 异步守卫 | mounted | 手写 `_disposed` | 框架接管 | `isClosed` 手动判 | autoDispose + ref 失效自动作废 |
| 输入流处理 | Timer + 序号 | Timer + 序号（进模型） | **EventTransformer 一锅端** | debounce worker + 手写序号 | Timer + 序号（进 Notifier） |
| 样板量 | 少（但传参地狱） | 中 | **最多**（event/state/copyWith） | **最少** | 中（codegen 可再减） |
| 可测性 | 差（只能 pumpWidget） | 好（纯 Dart 模型） | **最好**（blocTest 断言状态序列） | 好（controller 直接 new） | 好（ProviderContainer 无 UI 测试） |
| 编译期安全 | 高（就是传参） | 低（ProviderNotFound 运行时炸） | 低（同左） | **最低**（find 全靠运行时） | **最高**（provider 是顶层 final，引用即存在） |
| 学习曲线 | 零 | 平缓 | **陡**（单向数据流心智） | 最平（但坑在后头） | 中（ref/作用域概念） |

## 1. 同场景代码并排

### 1.1 场景③④：跨页共享的购物车 + 派生值（信号最强的对比）

**"加一件商品"这个动作，五种写法：**

```dart
// v0 setState：改共享对象 + 每个持有它的页面各自 setState（还要担心别的页面不知道）
widget.cart.add(product); setState(() {});

// v1 Provider：改字段 + 喊一嗓子，谁 watch 谁刷
class CartModel extends ChangeNotifier {
  void add(Product p) { /* 改 _items */ notifyListeners(); }
}

// v2 Bloc：算出全新不可变状态，emit；== 相等自动短路
class CartCubit extends Cubit<CartState> {
  void add(Product p) => emit(CartState(items: /* 基于旧 state 算新列表 */));
}

// v3 GetX：RxList 自动发流……除了改内部字段要手动 refresh 的坑
void add(Product p) { items[i].quantity += 1; items.refresh(); }

// v4 Riverpod：Notifier，state 整体替换（Bloc 式不可变，Provider 式调方法）
class CartNotifier extends Notifier<CartState> {
  @override CartState build() => const CartState();
  void add(Product p) => state = CartState(items: /* 算新列表 */);
}
```

**角标（字段级订阅 totalCount）：**

```dart
// v1
Selector<CartModel, int>(selector: (_, c) => c.totalCount, builder: ...)
// v2
BlocSelector<CartCubit, CartState, int>(selector: (s) => s.totalCount, builder: ...)
// v3（Obx 粒度小但无字段判等：items 一动必刷，哪怕 count 没变）
Obx(() => CartIconButton(count: cart.totalCount, ...))
// v4
ref.watch(cartProvider.select((s) => s.totalCount))
```

**跨路由 push 购物车页：**

```dart
// v0：构造函数把 cart 和回调一路递下去（S0 的痛点展品）
// v1/v2：.value re-provide（路由挂在 Navigator 下，不在版本子树里）
ChangeNotifierProvider.value(value: cart, child: const V1CartPage())
BlocProvider.value(value: cart, child: const V2CartPage())
// v3：不存在此问题——Get.find 全局直捞
Navigator.of(context).push(MaterialPageRoute(builder: (_) => const V3CartPage()));
// v4：container 不在树上，同样没这问题；但 ProviderScope 挂在版本根时，
//     push 出的路由要用 UncontrolledProviderScope 共享 container（v4 实现注释详述）
```

### 1.2 场景⑤：搜索防抖 + 丢过期（异步编排能力的分水岭）

| 方案 | 防抖 | 丢过期 | 代码位置 |
|---|---|---|---|
| v0/v1 | 手写 `Timer?.cancel + Timer(400ms)` | 手写请求序号 | v0 页面里 / v1 挪进 SearchModel |
| v2 | `events.debounce(400ms)` | `restartable()`（switchMap 掐旧处理器） | **一个 EventTransformer 声明完** |
| v3 | `debounce()` worker | **仍要手写序号**（无 switchMap） | SearchGetxController |
| v4 | 手写 Timer（riverpod 无内建防抖件） | 序号或 `ref` 失效判断 | SearchNotifier |

结论：**把"事件流"当一等公民的只有 Bloc**——输入流密集的场景（搜索、表单联动、节流上报）它的声明式编排优势最大；其余方案都在用命令式补丁逼近同一语义。

### 1.3 场景①：三态 + 分页（AsyncValue 的独门戏）

v1/v2/v3 都自己定义 loading/error/data 三个字段（或 status 枚举）+ hasMore/loadingMore。**Riverpod 是唯一把"异步三态"内建成类型的**：`AsyncNotifier` 的 state 是 `AsyncValue<T>`（loading/error/data 三态封死，还带 `isRefreshing` 等细分），UI 端 `switch (asyncValue)` 穷尽匹配，忘处理 error 态编译器直接提醒。四个方案手搓的 AsyncStateView 判断逻辑，riverpod 送了一半。

## 2. 重建范围：机制对比 + 实测

五方案收窄重建的机制光谱（从"作者点名"到"框架判等"）：

```
手工点名 ────────────────────────────────► 自动判等
GetX update(['id'])   Provider Selector    Bloc emit==短路
GetX Obx(块粒度)      context.select        + buildWhen/BlocSelector
                     Riverpod select       Riverpod provider 依赖图
```

**S2 课后练习实测**（归档于 `自测答案/S2-自测答案.md` 附录，RebuildBadge 计数）：列表页连续加购 5 件，`Selector` 版角标 badge 计数 +5、商品卡 badge **全程不动**；改成整页 `context.watch` 后商品卡 badge 随加购线性上涨（20 卡 × 5 次 = 100 次陪跑重建）。同构结论适用于 v2 的 BlocSelector 与 v4 的 select——**粒度即性能，且粒度是写出来的，不是方案送的**（v3 的 Obx 例外：粒度天然小，但缺字段判等，见 s4 §4.4）。

## 3. 样板量 / 可测性 / 学习曲线 / 团队协作

**样板量**（同一个购物车状态层的行数量级，MiniShop 实测）：GetX（RxList 一把梭）< setState ≈ Provider（ChangeNotifier + 手动 notify）< Riverpod（Notifier + 不可变 state）< Bloc（event + state + copyWith + Equatable，约 2 倍于 Provider）。Bloc 的溢价买的是纪律与可回放；GetX 的折扣赊的是运行时安全。

**可测性**（都比 v0 的"隔着 widget 戳"强一个时代）：
- Provider/GetX：模型/controller 直接 new，断言字段（v1 15 测、v3 14 测）。
- Bloc：**blocTest 断言状态值序列**（`expect: [A, B, C]`）——测的不是"最终对不对"而是"转移过程对不对"，回归定位最准（v2 14 测）。
- Riverpod：`ProviderContainer` + overrides，连 widget 层的依赖注入都能在纯 Dart 里测。

**学习曲线**：setState（零）→ GetX（半天上手，坑在三个月后）→ Provider（一天，心智≈SwiftUI）→ Riverpod（几天，ref/作用域/AsyncValue）→ Bloc(一周，单向数据流世界观 + transformer 并发模型)。

**团队协作**（规模越大权重越高）：Bloc 的强约定使 code review 有明确锚点（"这个副作用为什么在 builder 里？"）；Provider/Riverpod 依赖显式可查；GetX 的全局表 + 隐式订阅在 10 人以上团队里是排查成本黑洞——除非立死纪律。

## 4. 选型决策树

```
新项目选型
│
├─ 状态就几个局部开关，页面间几乎不共享？
│   └─ setState 就够（别为简历技术选型）
│
├─ 团队 iOS/SwiftUI 背景为主，中小项目，想要最平滑的第一站？
│   └─ Provider（心智≈EnvironmentObject；上限到了再迁 Riverpod，成本最低）
│
├─ 中大型多人协作 / 业务状态转移复杂 / 审计与回放有硬需求
│  （金融、订单流）/ 输入流编排密集？
│   └─ Bloc（样板税买纪律；配 freezed 减负）
│
├─ 个人项目 / 原型 / 小团队拼速度，接受运行时风险自己兜底？
│   └─ GetX（立纪律：只用状态半边、put/delete 配对、禁全家桶路由则更稳）
│
└─ 新项目无历史包袱，要编译期安全 + 异步状态是主要复杂度来源？
    └─ Riverpod（AsyncValue + autoDispose + 编译期存在性保证；本课程学员的 WanShop 主栈）
```

**存量项目**：先问"痛的是什么"。重建失控 → 上 Selector/buildWhen 级别的收窄，不用换方案；逻辑测不了 → 先把状态层搬出 UI（S2 干的事），任何方案都受益；provider 满天飞找不到依赖 → 考虑 Riverpod 的显式图。**换方案是最后的手段，且可以共存渐进**（见 §5）。

## 5. 迁移成本速查

| 从 → 到 | 成本 | 关键动作 |
|---|---|---|
| setState → Provider | 低 | 状态类抽出（ChangeNotifier），页面换 watch/read——v0→v1 的 diff 就是教程 |
| Provider → Riverpod | **低**（官方同作者，刻意平滑） | ChangeNotifier 可原样挂 ChangeNotifierProvider（riverpod 版）过渡；再逐个改 Notifier |
| Provider → Bloc | 中 | 模型方法 → 事件 + 处理器；可变字段 → 不可变 state；页面 Consumer → BlocBuilder（v1→v2 diff 即教程） |
| GetX → 任何树系方案 | **高** | 全局 find 点位遍布各层，依赖关系要先"考古"再显式化；全家桶用得越深越贵 |
| Bloc → Riverpod | 中 | state 类基本复用（都不可变），事件层摊平成方法；transformer 语义要手工补 |

共存策略：五方案在本工程共存零冲突的前提 = **shared 层纯净**（不 import 任何状态库）+ 每方案自带状态层。真实项目同理：新旧方案以"页面/模块"为边界共存，公共层保持方案中立，逐模块迁移。

## 6. 面试题汇总（20 题带答案要点）

**跨方案原理**

1. **所有树系方案共同的地基是什么？** InheritedWidget 的 O(1) 依赖注册（dependOnInheritedWidgetOfExactType）+ Listenable 通知。Provider/Bloc 的 provider 层都骑在它上面（s1/s2 详解）。
2. **"通知"和"重建"是两件事，各方案在哪一层收窄？** 通知：Rx 写入端去重（GetX）、emit == 短路（Bloc）；重建：Selector/select/buildWhen/BlocSelector 在"通知已到"后二次判等。粒度写在消费端。
3. **可变状态 + notify 与不可变状态 + emit 的本质区别？** 前者"变了什么"只有作者知道，监听者全量重查；后者新旧状态可 diff/判等/回放，声明式收窄与 blocTest 才有可能（S2 练习 2 ↔ S3 兑现）。
4. **跨路由拿不到状态的根因？** push 的路由挂在 Navigator 下，不在业务子树里——树系方案必须 re-provide（.value），树外方案（GetX 表/Riverpod 容器）天然免疫。
5. **异步回调撞已销毁对象，五方案各怎么防？** v0 mounted / v1 手写 _disposed / v2 框架接管（emit no-op）/ v3 isClosed 手动判 / v4 autoDispose + ref 失效。同一个病，防御层级逐步上移。

**选型题**

19. **给不同场景选方案并说理由**：银行 App 交易流（Bloc：审计/回放/纪律）、三人团队 MVP（GetX 或 Provider：速度）、SwiftUI 背景团队的中型电商（Provider 起步 → Riverpod）、异步密集的内容流 App（Riverpod：AsyncValue）。言之成理 + 说得出代价即合格。
20. **"你们项目为什么用 X？"的标准答法**：给出当时的约束（团队背景/项目规模/历史包袱）→ 对比过什么 → 选择付出的代价是什么、怎么兜底的。能说出**代价**的候选人比只会夸的可信十倍。
