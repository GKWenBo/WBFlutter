# L9 自测答案

**1. 引擎预热解决什么？代价？什么时候不该预热？**

解决 L8 的**冷启动白屏**：把"启动 Dart VM + 加载 App.framework + 跑 main + 建 widget 树"这段开销从"用户点开时"挪到"App 启动时"，用户体感是秒开。

代价是**内存常驻**——一个 Flutter 引擎几十 MB 量级，App 全程占着，即使用户一次都没点进 Flutter 页。而且 App 启动本身也变慢了一点。

不该预热的情况：模块是**低频边角功能**（一年用一次的活动页），常驻内存不划算；这时冷启动那点白屏可以接受。折中方案：进入某个业务域时才预热、离开时 `destroyContext()` 释放。

**2. 只 new 不 run 会怎样？为什么 run 要守卫？**

`FlutterEngine(name:)` 只是创建了引擎对象，**不会执行任何 Dart 代码**——`main()` 不跑、widget 树不存在、通道也没人应答。必须 `engine.run()` 才真正启动。

`run()` 要守卫是因为**重复调用会出问题**（引擎已在运行时再 run 属于非法状态）。本课用一个 `isWarmedUp` 标志位挡住：

```swift
func warmUp() {
    guard !isWarmedUp else { return }
    isWarmedUp = true
    engine.run()
    ...
}
```

**3. 为什么关掉页面后模块还记得 token？好事坏事？怎么重置？**

因为**关掉的只是"显示窗口"**（`FlutterViewController`），不是引擎。预热引擎是**常驻**的，Dart 侧的 isolate、widget 树、所有 State 对象**根本没被销毁**——`_token` 还在那个 State 里躺着。

**双刃剑**：
- 好处：秒开 + 状态延续，用户再进来还是刚才那个样子（像原生页一样）。
- 坏处：用户以为"关掉了应该重来"，实际没重置。可能泄漏上一个用户/上一单的数据——**这是真实事故的来源**。

要重置就得**显式清**：在通道上加一个 `resetModule` 方法，Dart 侧清空状态并回到首页，宿主在关闭页面时调一次（正是本课的课后练习）。

**4. 为什么模块不能自己 `Navigator.pop()` 关页面？**

因为这个 Flutter 页是**原生 present** 出来的：原生用 `fullScreenCover` / `present(vc)` 把 `FlutterViewController` 盖在了原生界面之上。在 **Flutter 自己的路由栈**里，这个页面是**根页**——`pop()` 会把根页弹掉，Flutter 侧只剩空白，而原生的那层 modal **还牢牢盖在屏幕上**。结果就是用户看到一片黑/白且退不出去。

原则：**谁 present 的，谁负责 dismiss**。所以模块只能通过通道"请求"宿主来关（`closePage`）。

**5. 热引擎上 `setInitialRoute` 为什么无效？正确做法？为什么要 navigatorKey？**

`initialRoute` 是 Dart 侧 `MaterialApp` 在**构建 widget 树那一刻**读取的值（来自 `PlatformDispatcher.defaultRouteName`）。预热引擎在 App 启动时就 `run()` 了，widget 树**早已按当时的值建好**。之后再 `setInitialRoute`，只是改了一个**没有人会再读**的值——所以页面纹丝不动（现象：点"打开 /detail"，开出来还是首页；本课实测踩到）。

**正确做法**：自定义通道方法，让 Dart 侧真正去 `Navigator` 上跳转：

```dart
case 'setRoute':
  moduleNavigatorKey.currentState?.pushNamedAndRemoveUntil(route, (_) => false);
```

**为什么需要全局 `navigatorKey`**：这个调用来自平台通道的回调，此刻**手上没有任何 `BuildContext`**（不在某个 widget 的 build 里），拿不到 `Navigator.of(context)`。`GlobalKey<NavigatorState>` 挂在 `MaterialApp(navigatorKey:)` 上，就能在任何地方通过 `.currentState` 拿到 NavigatorState。

用 `pushNamedAndRemoveUntil(..., (_) => false)` 而不是 `pushNamed`，是为了**清掉模块内的旧栈**——否则宿主反复打开，Flutter 侧会堆一叠用户返回不掉的页面。

一句话记法：**`setInitialRoute` 只对"还没跑起来的引擎"有效；跑起来了就得驱动 Navigator。**

**6. 什么时候需要多引擎？为什么用 `FlutterEngineGroup`？**

当宿主需要**同时并存**多个互不相干的 Flutter 界面时（比如两个 tab 各是一个 Flutter 模块，都要保持各自状态）。单引擎只有一棵 widget 树，做不到真正并存。

手动 new 多个 `FlutterEngine`：每个都是完全独立的运行时，**各自吃一份完整内存**（代码段、字体、资源全部重复）。

`FlutterEngineGroup` spawn 出来的引擎**共享**代码段、字体等只读资源，增量内存显著更小；同时每个引擎仍有**自己的 isolate、自己的 widget 树、自己的通道**（通道绑引擎这条规则不变）。所以：**需要多个并存 Flutter 界面时，用 `FlutterEngineGroup`。**

**7. 回顾整门课：L1 的 MethodChannel 和 L9 的宿主通道是什么关系？**

**机制完全相同，主客关系相反。**

| | L1（及 L2–L7） | L9 |
|---|---|---|
| 宿主 | Flutter App | **原生 App** |
| 谁嵌入谁 | Flutter 工程自带 `ios/Runner` | 原生工程嵌入 flutter module |
| 典型方向 | Flutter 调原生要能力（设备信息） | 双向：模块要宿主的登录态；宿主要模块的状态/驱动它换页 |
| 通道挂在哪 | `AppDelegate` 里 App 的引擎上 | 宿主自己持有的**常驻引擎**上 |
| 底层 | `MethodChannel` + `StandardMethodCodec` | **一模一样** |

这就是整门课的收束：从 L1 学的那条 `MethodChannel`，到 L9 的混合 App 宿主通道，**技术底座从头到尾是同一套**——变的只是"谁是宿主、谁在嵌谁"。理解了这一点，无论是 Flutter 里嵌原生（L1–L7），还是原生里嵌 Flutter（L8–L9），都是同一个心智模型的两面。
