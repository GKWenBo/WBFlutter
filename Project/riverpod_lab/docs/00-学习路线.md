## 3. 为什么全用 codegen

手写和 codegen 的运行时行为完全一样，差别在声明方式：

```dart
// 手写（2.x 时代主流）
class Counter extends Notifier<int> {
  @override
  int build() => 0;
}
final counterProvider = NotifierProvider<Counter, int>(Counter.new);

// codegen（本工程）
@riverpod
class Counter extends _$Counter {
  @override
  int build() => 0;
}
// 生成：counterProvider（自动带上 autoDispose）
```

codegen 真正省掉的是三件事，而不只是那一行 `final`：

- **命名不用记**：类 `Counter` → `counterProvider`，函数 `appVersion` → `appVersionProvider`；
- **family 参数变成 build 的形参**：不用再写 `NotifierProvider.family<...>` 那一长串泛型；
- **默认 autoDispose**：注意这是和手写版相反的行为（手写默认常驻），也是 2.x 迁移过来最常见的坑。

代价是每次改动要跑一次 build_runner。工程里已经配好，日常开发建议另开一个终端跑 `dart run build_runner watch`。

## 4. codegen 工作流

```bash
# 一次性生成（本工程用这个）
dart run build_runner build

# 开发时常驻，保存即生成
dart run build_runner watch

# 生成物错乱/删过文件时，先清再生成
dart run build_runner clean
dart run build_runner build
```

生成物长什么样？`lib/shared/app_info.g.dart` 里能看到注解被翻译成的真实 provider 类，注意这一行：

```dart
super(
  ...
  isAutoDispose: true,  // codegen 的默认值，手写版默认是 false
  ...
);
```

## 5. 目录约定

```
lib/features/<feature>/
├── <feature>_provider.dart   # 状态声明与业务逻辑
├── <feature>_page.dart       # UI，只读 provider / 调 notifier 方法
└── ...
```

- 一个 feature 一个目录，不建 `controllers/`、`services/` 这类空壳分层；
- 跨 feature 复用的东西才放 `lib/shared/`；
- provider 文件命名统一带 `_provider` 后缀，`grep` 时一眼能找到全部状态源。

## 6. 调试技巧

- **看谁在重建**：在 `build` 里 `debugPrint('$runtimeType build')`，再配合热重载观察；S1 的 select 示例就靠这个对比。
- **看 provider 图**：Flutter DevTools 里安装 Riverpod 扩展（3.x 自带 devtool 支持），可以查看 provider 实例、依赖关系与重建次数。
- **provider 没更新**：先确认用 `ref.watch` 而不是 `ref.read`；回调里才用 `read`。
- **报 `No ProviderScope found`**：`main()` 里最外层忘记包 `ProviderScope`，或测试里 `pumpWidget` 没用 `ProviderScope` 包。
