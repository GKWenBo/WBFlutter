# S4 自测答案（对照版）

> 2026-07-16 归档（一次性完成模式，讲师直接给出对照版）。

### 1. Obx 的依赖收集怎么实现？为什么闭包没读 Rx 抛错、回调里读不算？

build 闭包执行期间，GetX 把全局 `RxInterface.proxy` 指向当前 Obx 的观察者；每个被**读取**的 Rx 在 getter 里把自己登记给 proxy；build 结束 proxy 撤下。闭包没读任何 Rx → 登记表为空，这个 Obx 永远不会刷新，GetX 直接抛 "improper use of GetX" 拒绝装傻。回调执行时 proxy 早已撤下，读 Rx 只是普通取值，不产生订阅。

### 2. RxList 改元素内部字段为什么界面不动？两种解法？

RxList 只拦截自身的方法（add/removeAt/[]= 等），元素对象内部的字段赋值它无从感知——流不发，Obx 不刷。解法一：改完手动 `items.refresh()` 强发一次（运行时补救，忘一处坏一处）；解法二：元素用不可变对象，"改"变成"整项替换"（`items[i] = items[i].copyWith(...)`，`[]=` 是 RxList 自己的方法必发流）——v2 的 CartLine 思路，类型级根治。

### 3. update() 无参和 update(['id']) 的关系？

隔离的两张监听表：无参 update 只通知**无 id** 的 GetBuilder，带 ids 只通知对应分组，互相刷不到。工程里列表控制器的通知全部显式带 ids，就是防止"以为 update() 是全刷"的坑；顺带把外层 init 宿主 GetBuilder（无 id）做成了永不重建的壳。

### 4. put/lazyPut/find/delete 的生命周期时机？

`Get.put`：写表并**立即**创建、触发 onInit。`Get.lazyPut`：写表存工厂，**首次 find** 才创建触发 onInit。`Get.find`：查表返回（未注册即抛异常）。`Get.delete`：触发 onClose 并出表。没有 GetMaterialApp 的路由钩子时没有自动 delete——手动配对，或用 GetBuilder(init:) 的 autoRemove。

### 5. debounce worker 替了什么？丢过期为什么还要序号？

替掉 v1 手写的 `Timer?.cancel + Timer(400ms)` 防抖。但 worker 只解决"什么时候开枪"，不解决"开出去的两枪谁作数"——GetX 没有 switchMap/restartable，慢请求的过期响应仍会回来，只能手写 `seq != _seq` 拦（v1 同款）。对照 v2：`debounce + restartable` 一个 transformer 两件事全办。

### 6. isClosed 守卫防什么？三种形态对比？

防"controller 已被 delete（onClose 已跑），在途异步回来再 update/改 Rx"撞已销毁对象。v1：自己造标志位自己判（`_disposed`）；v2：框架全接管（close 后 Emitter 变 no-op，restartable 还主动掐旧处理器）；v3：框架给了 `isClosed` 现成标志位，**但每个异步回来处自己判**——介于两者之间。

### 7. v3 为什么零 re-provide？账单三条？

依赖住在树外全局表，`Get.find` 不经过 Element 树的向上查找——路由边界对它不存在，v1/v2 的 `.value` 自然消失。账单：①运行时安全（忘 put/早 delete = 炸时才知道）；②依赖关系编译器/Inspector 均不可见；③生命周期手动管（V3ShopRoot 的 put/delete 配对、测试的 Get.reset），忘一处就泄漏或版本串味。

### 8. 不用 GetMaterialApp 损失什么？为什么主导航不绑？

损失：`Get.to` 系全局路由、路由绑定的 smart management（自动回收依赖）、`Get.snackbar` 等依赖全局 navigatorKey 的工具。主导航不绑的原因：StateLab 五版本共存，基础设施必须方案中立（设计文档 §7）；顺带证明 GetX 状态管理可以脱离它的路由体系单独用——真实项目渐进引入/渐进撤出时这很重要。

### 9. "count 没变角标不刷"能开箱做到吗？

不能。Rx 的去重在**写入端**（赋相同值不发流），而 totalCount 是派生 getter，没有自己的盒子——items 一发流，订阅 items 的 Obx 必重建再现算。要字段级判等得自己动手：totalCount 单独做 RxInt，用 `ever(items, ...)` 同步（RxInt 写入端去重这时才生效）。对照 v1 `Selector`/v2 `BlocSelector` 一行搞定——这是 GetX 工具箱里缺的那件。

### 10. 争议五条 + 立场

①全局单例路由绕开树的作用域；②依赖运行时才可见；③生命周期与树脱钩靠人管；④隐式魔法难排查（"为什么这个 Obx 不刷/总刷"）；⑤路由+状态+DI 全押单包的维护风险。立场参考（讲师版）：个人项目/原型/小团队快速出活——用，很香；中大型多人协作——依赖可见性和编译期保障的价值随团队规模超线性增长，倾向 Provider/Bloc/Riverpod，或至少立死纪律只用 GetX 的状态管理半边。言之成理即可。

## 课后练习对照（理论推演版）

**练习 1（手动挡改自动挡）**：全 `.obs` 版代码更短（省掉所有 update 调用），但失去 id 定向刷新——loadingMore 翻转会惊动所有读了它的 Obx；且 `items`、`loading`、`hasMore` 三个 Rx 在一次 loadFirst 里各发各的流，Obx 可能一帧内多刷。结论：状态转移清晰、单页消费 → 手动挡更可控；多处零散订阅 → 自动挡更省事。

**练习 2（字段级判等）**：`final totalCount = 0.obs;` + onInit 里 `ever<List<CartItem>>(items, (_) => totalCount.value = _calc());`（items.refresh 也会触发 ever）。角标 Obx 改读 `totalCount.value`——数量没变时 RxInt 写入端去重，角标不刷。代码量对比 Selector 的一行，直观感受"缺件"。

**练习 3（带去 S6）**：GetX 的表是**运行时全局可变**的（谁都能 put/delete/覆盖，类型是查表 key，查不到才知道）；Riverpod 的 provider 图是**编译期声明的顶层 final 常量**（引用即存在，类型由泛型静态保证，作用域由 ProviderScope 控制，依赖关系 ref.watch 显式可追踪）。同是"搬出树"，一个搬进了可变的全局 Map，一个搬进了不可变的声明式图——安全性口碑差在这。
