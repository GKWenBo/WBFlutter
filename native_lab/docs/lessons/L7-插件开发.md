# L7 插件开发（抽出 nl_device_kit）

> 企业场景：前 6 课的桥都长在**主 app 里**——channel 在 `lib/lessons/*` 手写、原生实现塞在 `AppDelegate`/`MainActivity`、注册也得**逐条手写**。可"设备信息""埋点""网络状态"这些能力，别的 App、别的团队也要用。总不能每个项目复制粘贴一遍。本课把 **L1 的设备信息桥抽成独立插件包 `nl_device_kit`**：一个能被任意 Flutter 工程 `path`/git/pub.dev 依赖的可复用单元——企业"自家插件库"的诞生。**L1 手写版原样保留**，两页并排就是"散在 app 里的桥"vs"打包成插件的能力"的活教材。

## 一、本课要掌握什么

**1. 插件 = 把"Dart API + 原生实现"打包成一个可复用包。**

它不是新通信机制——底层还是 L1 那套 MethodChannel。变的是**工程组织**：能力从 app 里搬进 `plugins/nl_device_kit/`，有自己的 `pubspec.yaml`、`lib/`、`ios/`、`android/`，能被别的工程依赖。

**2. ★ 自动注册 vs 手写注册（本课最核心的差异）。**

| | 前 6 课（app 内嵌桥） | L7（插件） |
|---|---|---|
| 原生注册 | `AppDelegate`/`MainActivity` 里**手写** `FlutterMethodChannel(...)` + `setMethodCallHandler` | 实现 `FlutterPlugin`，由 **GeneratedPluginRegistrant 自动**调 `register(with:)`/`onAttachedToEngine` |
| 你要做的 | 每条桥手动登记一次 | **什么都不用做**——`flutter pub get` 后生成代码自动登记 |
| channel 生命周期 | 跟 App/引擎手动管 | 插件的 `onAttachedToEngine`/`onDetachedFromEngine` 托管 |

验证点：L7 页能取到设备信息，而我们**没在 AppDelegate 写一行注册**——这就是自动注册在起作用（`GeneratedPluginRegistrant.m` 里能看到 `[NlDeviceKitPlugin registerWithRegistrar:...]`）。

**3. 三层结构（官方模板默认）= 联邦插件的接缝。**

```
NlDeviceKit（公开 API，消费方只认它）
   └─委托→ NlDeviceKitPlatform.instance（抽象接口）
              └─默认是→ MethodChannelNlDeviceKit（MethodChannel 实现）
```

- 公开 API 与实现解耦：消费方调 `NlDeviceKit().getDeviceInfo()`，不关心底层。
- 抽象接口这层缝的价值：换实现（不同平台/不同后端/测试 mock）只替换 `instance`，公开 API 不变。这正是**联邦插件**的思想；完整联邦会把接口和各平台实现拆成多个包（camera/video_player 那样），本课单包演示接缝，多包留作延伸。

**4. path 依赖：企业"自家插件库"的雏形。**

app 的 `pubspec.yaml`：
```yaml
  nl_device_kit:
    path: ../plugins/nl_device_kit
```
本地开发用 `path`；对外分发改成 `git:` 或发布到 `pub.dev`（私有库用私有 pub 服务器）。

**5. package / plugin / FFI plugin：别把三个概念混着说。**

| 类型 | 有没有原生代码 | 创建命令 | 例子 |
|---|---|---|---|
| **package**（纯 Dart 包） | 无 | `flutter create -t package` | `intl`、`collection`、自家的工具库/UI 组件库 |
| **plugin**（插件） | **有**（Swift/Kotlin/ObjC/Java） | `flutter create -t plugin` | 本课的 `nl_device_kit`、`shared_preferences` |
| **FFI plugin** | 有（C/C++，走 `dart:ffi` 不走 channel） | `flutter create -t plugin_ffi` | 加解密、图像处理、封装既有 C 库 |

再加一个第四种：**module**（`-t module`），那是 L8 的主角——被原生 App 反过来依赖的可嵌入模块。

**6. 联邦插件（federated plugin）的三块拼图。**

本课单包演示了"公开 API / 抽象接口 / 默认实现"的接缝，完整联邦会把它们拆成多个**独立发布的包**：

| 角色 | 内容 | 例子 |
|---|---|---|
| **app-facing package** | 消费方唯一依赖的门面包 | `camera` |
| **platform interface package** | 抽象接口 + token 校验，各实现共同遵守的契约 | `camera_platform_interface` |
| **platform implementation package** | 某个平台的具体实现 | `camera_android`、`camera_avfoundation`、`camera_web` |

拼图靠 pubspec 的两个字段接起来：实现包用 **`implements: camera`** 声明"我是 camera 的某平台实现"；门面包在 `platforms:` 里用 **`default_package:`** 指定各平台默认用谁——被门面包这样指定的实现叫 **endorsed（背书）实现**，用户只依赖门面包就能自动带上它。第三方也可以发一个**非背书**实现（比如自研的 `camera_myvendor`），使用者显式依赖它即可覆盖。

价值：**换实现不动调用方**、各平台可以独立发版、第三方能替换官方实现。代价是包多、版本矩阵复杂——**能力单一、只有你自己团队用的插件，单包就够了**（本课的选择）。

另外还有一个 `dartPluginClass`：如果某个平台的实现**纯 Dart 就能完成**（不需要原生代码），可以在 pubspec 里声明它，框架会自动把 `Platform.instance` 注册成这个类——这就是"没有原生代码的平台实现包"的做法。

## 二、控件 / API 速查表

### 工程 & 结构（本课新东西）

| API | iOS 类比 | 用法 & 关键点 | 坑 |
|---|---|---|---|
| `flutter create --template=plugin` | 新建一个 Framework/Pod 工程 | `--platforms=ios,android --org com.wenbo -i swift -a kotlin` | 会生成 `example/`，path 依赖用不上可删 |
| `pubspec: flutter: plugin: platforms:` | 声明支持平台 + 入口类 | `ios/android` 各配 `pluginClass`（+ android `package`） | 类名/包名写错 → 自动注册找不到类 |
| `path:` 依赖 | 本地 Pod `:path =>` | app pubspec 指向 `../plugins/xxx` | 改插件后 app 要 `flutter pub get` |

### Dart 三层

| API | 说明 | 坑 |
|---|---|---|
| `NlDeviceKit`（公开门面） | 消费方唯一入口，三方法委托 platform instance | — |
| `NlDeviceKitPlatform extends PlatformInterface` | 抽象接口 + `static instance` + token 校验 | 子类要 `extends` + `MockPlatformInterfaceMixin`（测试）才过 token |
| `MethodChannelNlDeviceKit` | 默认实现，`MethodChannel('nl_device_kit')` | channel 名独立于 L1，避免撞名 |
| `export 'src/device_info.dart'` | 让消费方 import 一个库拿到 model | 忘了 export → 消费方引用不到 DeviceInfo |

### 原生侧

| API | iOS (Swift) | Android (Kotlin) |
|---|---|---|
| 入口 | `FlutterPlugin.register(with:)` | `FlutterPlugin.onAttachedToEngine(binding)` |
| 挂 handler | `registrar.addMethodCallDelegate(self, channel:)` | `channel.setMethodCallHandler(this)` |
| 拿 context | `Bundle.main` 直接用 | `binding.applicationContext`（存字段） |
| 卸载 | 框架托管 | `onDetachedFromEngine` 里 `setMethodCallHandler(null)` |

## 三、代码地图

**插件包 `plugins/nl_device_kit/`**

## 四、测试怎么写

三层结构让测试有两个抓手：

```dart
// ① mock platform interface（这层缝的测试价值）：不碰真 channel，验证公开 API 转发
class _MockPlatform extends NlDeviceKitPlatform with MockPlatformInterfaceMixin {
  @override Future<DeviceInfo> getDeviceInfo() async => const DeviceInfo(model: 'iPhone', ...);
}
NlDeviceKitPlatform.instance = _MockPlatform();
expect((await NlDeviceKit().getDeviceInfo()).model, 'iPhone');

// ② mock channel：验证 MethodChannel 实现把原生 Map 收成强类型（对照 L1 的测法）
setMockMethodCallHandler(impl.methodChannel, (call) async => {'model': 'Pixel', ...});
expect((await impl.getDeviceInfo()).systemName, 'Android');
```

- `MockPlatformInterfaceMixin` 绕过 `PlatformInterface` 的 token 校验（否则塞 mock 会被拒）。
- App 侧：L7 页 build 冒烟（不点按钮，避免触发真 channel）。
- 插件包有自己的 `flutter test`，和 app 的分开跑。

## 五、双端对照（Swift vs Kotlin）

| 维度 | iOS (Swift) | Android (Kotlin) |
|---|---|---|
| 协议 | `NSObject, FlutterPlugin` | `FlutterPlugin, MethodCallHandler` |
| 注册入口 | `static func register(with:)` | `onAttachedToEngine(binding)` |
| 挂 handler | `registrar.addMethodCallDelegate(self, channel:)` | `channel.setMethodCallHandler(this)` |
| 分发 | `handle(_:result:)` `switch call.method` | `onMethodCall(call, result)` `when` |
| context | `Bundle.main` / `UIDevice.current` | `binding.applicationContext` |
| 自动注册 | `GeneratedPluginRegistrant` 调 `register(with:)` | 同名，v2 embedding 自动 attach |
| 清理 | 框架托管 | `onDetachedFromEngine` 解绑 |

> 本课 iOS 主讲、模拟器验证；Android 完整对照实现（本机不强制跑安卓）。

## 七、课后练习

给插件加一个新能力 `getDeviceModelName()`（返回更细的机型串，如 iOS 的 `iPhone16,2`），走一遍完整回路：

1. `platform_interface` 加抽象方法 `Future<String> getDeviceModelName()`；
2. `method_channel` 实现里加 `invokeMethod('getDeviceModelName')`；
3. iOS 用 `utsname`/`sysctlbyname("hw.machine")`、Android 用 `Build.MODEL`/`Build.DEVICE` 各加一个 case；
4. `NlDeviceKit` 暴露该方法；
5. app L7 页加一行显示；
6. 补一条 mock platform 的测试。

练的是"插件里加方法 → 接口/实现/两端/调用点一起动"的完整约束——这正是插件 API 演进的日常。

## 八、面试高频题（附答案）

> 面试语境：这一课的题常以"你们团队怎么复用原生能力"或"你写过插件吗"开场。**能讲清自动注册原理和联邦结构，是"做过基建"和"只调过 API"的分水岭。**

**Q1. Flutter 插件的自动注册是怎么实现的？我什么都没写，原生侧怎么就注册上了？**

链路是：`pubspec.yaml` 里插件声明了 `flutter: plugin: platforms: ios: pluginClass: NlDeviceKitPlugin` → `flutter pub get` 时工具扫描依赖树里所有插件，**生成 `GeneratedPluginRegistrant`**（iOS 是 `.m`，Android 是 `.java`）→ 引擎启动时调用它，它挨个调每个插件的 `register(with:)` / `onAttachedToEngine(binding)` → 插件在这里建自己的 channel 并挂 handler。

对照前六课：我们是在 `AppDelegate`/`configureFlutterEngine` 里**手写**注册；插件化之后这一步由生成代码替你做了。

**面试延伸点**：这也解释了 **add-to-app 里自己 new 的引擎为什么必须手动调 `GeneratedPluginRegistrant.register(with: engine)`**（L9）——自动注册只发生在"有人调它"的时候，你自己创建的引擎没人替你调。

**Q2. 插件的 channel 名该怎么取？和 app 里的桥撞名会怎样？**

同名 channel **后注册的 handler 会静默覆盖先注册的**，不报错——症状是"某个功能莫名其妙调到了别人的实现上"，极难排查。

所以插件的 channel 名要**足够独特**：用包名/反域名前缀（本课是 `nl_device_kit`），绝不能用 `device_info`、`utils` 这种通用词。这也是为什么本课刻意让插件的 channel 名**独立于 L1** 的那条。

**Q3. `NlDeviceKit` → `NlDeviceKitPlatform` → `MethodChannelNlDeviceKit` 三层各干什么？中间那层能去掉吗？**

- 门面层（`NlDeviceKit`）：消费方唯一入口，API 稳定；
- 抽象接口层（`NlDeviceKitPlatform`）：契约 + `static instance`，**这是可替换的接缝**；
- 实现层（`MethodChannelNlDeviceKit`）：默认的 channel 实现。

去掉中间层也能跑，但会丢三样：① **换实现的能力**（不同平台不同实现、mock 实现、未来换 Pigeon/FFI 实现都要改门面）；② **测试注入点**（要测就得去 mock 真 channel）；③ **拆成联邦包的可能**。

**一句话：那层缝是给"未来会变的部分"留的。**

**Q4. 什么是联邦插件？什么时候值得拆？**

app-facing 包 + platform interface 包 + 各平台实现包，用 `implements:` 和 `default_package:` 串起来（被门面包指定的实现叫 **endorsed**）。典型例子是 `camera` 系列。

值得拆的信号：**平台多**（iOS/Android/Web/Desktop）、**各平台由不同人/不同团队维护**、**需要允许第三方替换实现**、**各平台要独立发版节奏**。

不值得拆：能力单一、只有自家用、双端由同一个人维护——**这时候单包 + 三层结构就是最佳性价比**（本课的选择）。回答时敢说"我们没拆，因为不值得"，比硬套架构更显判断力。

**Q5. 测试里为什么要 `MockPlatformInterfaceMixin`？`PlatformInterface` 的 token 校验是干嘛的？**

`PlatformInterface` 要求子类必须 **`extends`** 而不是 `implements`，并在构造时校验一个 token。目的是**防止第三方用 `implements` 假冒接口**——因为 Dart 里任何类都能被 `implements`，一旦接口未来新增方法，`implements` 的实现类会**静默地不兼容**（编译报错甚至运行期缺方法），而 `extends` 能继承默认实现，接口才可以安全演进。

测试里的 fake 又确实需要绕过这条限制，所以官方给了 `MockPlatformInterfaceMixin` 作为**唯一合法的后门**。

**Q6. 插件的原生侧生命周期有哪些回调？Android 上要用到 Activity 怎么办？**

- 两端通用：`onAttachedToEngine` / `onDetachedFromEngine`（iOS 侧由 `register(with:)` + 框架托管），**在 detach 里要把 handler 置空、释放资源**。
- Android 独有：需要 `Activity`（弹权限框、`startActivityForResult`）的插件要实现 **`ActivityAware`**，拿 `onAttachedToActivity` / `onDetachedFromActivityForConfigChanges` / `onReattachedToActivityForConfigChanges` / `onDetachedFromActivity` 四个回调——因为 **Activity 会因为旋转屏幕等配置变更而重建，而引擎不会**。这是 iOS 工程师最容易忽略的双端差异之一。

顺带一提：Android 的 **v1 embedding**（老的 `registrar` 静态注册）已被淘汰，现在都是 **v2 embedding**（`FlutterPlugin` 接口）。看到老插件只有 v1 实现，就是该换掉它的信号。

**Q7. 插件怎么分发和版本管理？**

- **本地开发**：`path:` 依赖，改完插件在 app 里 `flutter pub get` 即可，调试最快；
- **团队内共享**：`git:` 依赖（可锁 `ref` 到 tag/commit），不用搭基础设施；
- **规模化**：发到 **pub.dev**（开源）或**私有 pub 服务器**（内部），配合语义化版本 `^x.y.z` 约束。

API 演进纪律：**加方法是兼容的、改签名/删方法是破坏性的**——后者要升主版本号。插件里加方法的完整回路是"接口 → 默认实现 → 双端原生 → 门面 → 调用方 → 测试"，一处不改就编译报错，这正是三层结构给你的保护。
